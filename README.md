# Recreating PIX

Build a PIX-style transfer flow where the API receives a transfer, responds immediately, and a background worker settles the money asynchronously.

The difficult part is not the CRUD. It is what happens when 200 transfers from the same account arrive at the same time and the account only has enough balance for half of them: no money can be created, no money can disappear, and no account can ever end up with a negative balance.

## How It Works

```text
                    ┌──────────────────────────────────────────────┐
  POST /transfers   │                  YOUR API                    │
  ─────────────────►│               port 3000                      │
  { payerId,        │                                              │
    payeeId,        │   validate payload ──► save as pending       │
    amount,         │   DO NOT check balance            │            │
    idempotencyKey }│                              │               │
  ◄─────────────────│   respond immediately ───────┤               │
   201 pending      │                              │               │
                    └──────────────────────────────┼───────────────┘
                                                   │
                                                   ▼
                                    ┌──────────────────────────┐
                                    │       PostgreSQL         │
                                    │   accounts · transfers   │
                                    └──────────────────────────┘
                                                   ▲
                                                   │  picks pending
                    ┌──────────────────────────────┼───────────────┐
                    │                  WORKER      │               │
                    │              (background)    │               │
                    │                              ▼               │
                    │              does payer balance cover it?   │
                    │                ├── yes ──► debit payer       │
                    │                │           credit payee       │
                    │                │           mark completed    │
                    │                └── no ──► mark failed         │
                    │                            insufficient_funds │
                    │                            move no money      │
                    └──────────────────────────────────────────────┘

  GET /transfers/{id}              ──►  current transfer status
  GET /accounts/{id}/statement     ──►  balance + completed transfers
```

The lifecycle of a transfer:

```text
                    worker: balance is sufficient
   pending ─────────────────────────────────────► completed
      │
      │             worker: balance is insufficient
      └─────────────────────────────────────────► failed
                                                   failureReason:
                                                   insufficient_funds
```

Once a transfer is `completed` or `failed`, its state must never change again — and it must never be settled twice.

## Data Model

**All monetary values are integers representing cents.** R$25.00 is `2500`. Never use floating-point numbers anywhere — not in JSON, not in the database, and not in intermediate calculations.

### Account

| Field     | Type   | Description                                                |
| --------- | ------ | ---------------------------------------------------------- |
| `id`      | string | Account identifier, defined by whoever creates the account |
| `balance` | int    | Balance in cents                                           |

### Transfer

| Field            | Type   | Description                              |
| ---------------- | ------ | ---------------------------------------- |
| `id`             | string | Generated by the API                     |
| `payerId`        | string | Account sending the money                |
| `payeeId`        | string | Account receiving the money              |
| `amount`         | int    | Amount in cents, always positive         |
| `idempotencyKey` | string | Deduplication key provided by the client |
| `status`         | string | `pending`, `completed`, or `failed`      |
| `failureReason`  | string | null                                     | Populated only when `failed` |
| `createdAt`      | string | ISO 8601 timestamp in UTC                |

```json
{
    "id": "9c1f8b2e-...",
    "payerId": "acc-1",
    "payeeId": "acc-2",
    "amount": 2500,
    "idempotencyKey": "abc-123",
    "status": "pending",
    "failureReason": null,
    "createdAt": "2026-07-24T12:00:00Z"
}
```

## Endpoints

| Method | Route                      | Description                                              |
| ------ | -------------------------- | -------------------------------------------------------- |
| `GET`  | `/health`                  | Health check → `{ "status": "ok" }`                      |
| `POST` | `/accounts`                | Creates an account with an initial balance → `201`       |
| `POST` | `/transfers`               | Receives a transfer and responds immediately → `201`     |
| `GET`  | `/transfers/{id}`          | Retrieves a transfer and its status → `200`              |
| `GET`  | `/accounts/{id}/statement` | Statement: current balance + completed transfers → `200` |

### `POST /accounts`

This endpoint exists to make it possible to set up test scenarios.

Request body:

```json
{
    "id": "acc-1",
    "balance": 100000
}
```

Returns `201` with the created account.

- Missing or empty `id`, missing `balance`, negative `balance`, or non-integer `balance` → `422`
- `id` already exists → `409`

### `POST /transfers`

**Receive and respond immediately without processing the transfer.** The transfer is created with `pending` status, and the worker is responsible for moving the money.

```json
{
    "payerId": "acc-1",
    "payeeId": "acc-2",
    "amount": 2500,
    "idempotencyKey": "abc-123"
}
```

Returns `201` with the transfer in `status: "pending"`.

- If the `idempotencyKey` already exists → `200` with the original transfer, without creating another transfer or modifying the existing one
- Invalid payload → `422`: missing field, `amount` less than or equal to zero, non-integer `amount`, nonexistent `payerId` or `payeeId`, or `payerId` equal to `payeeId`

**Balance is not checked here.** A transfer of R$1,000.00 from an account with only R$10.00 still receives `201 pending` normally. The worker rejects it when attempting to settle it.

### `GET /transfers/{id}`

Returns `200` with the transfer and its current status, or `404` if it does not exist.

### `GET /accounts/{id}/statement`

Returns `200` with the account's current balance and all completed transfers involving the account — both transfers it paid and transfers it received.

Order: most recent first.

Returns `404` if the account does not exist.

```json
{
    "accountId": "acc-1",
    "balance": 97500,
    "transfers": [
        {
            "id": "9c1f8b2e-...",
            "payerId": "acc-1",
            "payeeId": "acc-2",
            "amount": 2500,
            "idempotencyKey": "abc-123",
            "status": "completed",
            "failureReason": null,
            "createdAt": "2026-07-24T12:00:00Z"
        }
    ]
}
```

Only `completed` transfers are included. `pending` and `failed` transfers are excluded.

## The Worker

The worker runs in the background and consumes `pending` transfers in the order they arrived.

For each transfer:

- **Sufficient balance:** debit the payer, credit the payee, and mark the transfer as `completed`.
- **Insufficient balance:** mark the transfer as `failed` with `failureReason: "insufficient_funds"` and **move no money at all**.

The balance check happens here, at settlement time — never in the `POST` request.

Between receiving a transfer and processing it, the account may have been emptied by another transfer. That race condition is exactly where the challenge lies.

Where the worker runs is up to you: a thread in the same process, a separate container, multiple replicas, or another architecture.

The only requirement is that the same transfer must never be settled twice.

## Invariants

These must hold under every scenario and any level of concurrency:

1. **Conservation** — the sum of all account balances at the end must be exactly equal to the initial total. No money is created and no money is lost.
2. **Balance never goes negative** — no account can ever end up with a negative balance.
3. **Idempotency** — sending the same `idempotencyKey` N times results in exactly one debit.
4. **Statement consistency** — the returned balance must match the initial balance plus completed incoming transfers minus completed outgoing transfers.
5. **Non-blocking response** — `POST /transfers` must respond without waiting for settlement.
